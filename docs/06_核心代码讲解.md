# 06 核心文件逐个讲解与扩展分支核对

[返回目录](README.md) · [上一篇](05_推理流程.md) · [下一篇：源码阅读顺序](07_源码阅读顺序.md)

本篇作为边打开源码边阅读的手册。主线的完整 shape 和公式分别在 03、04，这里重点解释关键语句之间的联系，以及“定义了但没有真正接入”的功能。

## 1. `minionerec/datasets/recommendation.py`：决定模型实际上在学什么

源码：[minionerec/datasets/recommendation.py](../minionerec/datasets/recommendation.py)。

### `BaseDataset`、`CSVBaseDataset`、`JSONBaseDataset`

`BaseDataset` 保存 tokenizer 包装器、最大长度、类别、test、dedup 等状态。`CSVBaseDataset` 读 CSV，可按 seed 抽样；`JSONBaseDataset` 读商品元数据和 SID 索引。它们负责公共加载逻辑，具体任务交给子类的 `pre`。

关键不是继承本身，而是 `get_inputs()` 会逐行预先调用 `pre()`。一旦构造完成，`__getitem__` 就返回缓存字典。因此修改 prompt、label 或随机任务选择，要理解它是在初始化时生效，而不是训练每个 epoch 都重新生成。

`Tokenizer.encode` 是对外部 tokenizer 的轻量包装，控制 BOS/EOS；它没有实现分词算法。它直接访问 `t[0]`、`t[-1]`，也没有普遍处理编码结果为空的情况。

### `SidSFTDataset.get_history` 与 `pre`

`get_history` 把 CSV 的列表字符串解析成历史 SID，用逗号连接，并返回目标 SID 加换行。`pre` 的核心顺序是：

```python
target_item = history['output']
history['output'] = ''
prompt = self.generate_prompt(history)
# 编码 instruction + prompt
golden_tokens = self.tokenizer.encode(target_item, bos=False, eos=True)
# 拼接 prompt 和答案
labels = [-100] * input_prompt_len + tokens[input_prompt_len:]
```

先把答案清空再生成 prompt，防止把答案当成已知条件。训练时答案仍拼入 input_ids，是为了同时计算答案多个位置的 next-token loss；因果 mask 负责防止未来 token 被看到。`negative_prompt_ids` 在此只是未继续使用的局部变量，并不是已经接通的负样本学习。

`dedup` 在主 SID 类里主要体现为返回一个“目标是否等于最后历史商品”的标记，不会自动删除重复样本。字段名不等于过滤操作。

### `SidItemFeatDataset.__init__/generate_prompt/pre`

把商品索引和标题关联，生成双向问答。`sid2title` 与 `title2sid` 都是普通字典：相同 SID 或相同标题会覆盖旧值，所以样本数不一定严格等于 `2×商品数`。只拼前三层 SID，长 SID 的附加消歧码没有进入映射。

训练它的原因是让语言模型知道代码与自然语言之间的联系；当前实现仍使用生成式交叉熵，没有向量对比 loss。

### `FusionSeqRecDataset.get_history/pre`

历史用 SID，目标通过 SID 查标题。名字里的 Fusion 不表示多路网络融合，而是输入／输出表示形式的组合。构造时处理描述，类里也有 `generate_prompt_description`，但当前 `pre` 固定调用 `generate_prompt_title`。因此默认训练任务是历史 SID → 下一标题。

### RL 与其他数据集索引

| 类 | `pre` 的产物／主要任务 | 默认接入情况 |
| --- | --- | --- |
| `SidDataset` | 字符串 prompt/completion；历史 SID → SID | `minionerec/training/rl.py` 使用 |
| `RLTitle2SidDataset` | 标题或描述 → SID | `minionerec/training/rl.py` 使用 |
| `RLSeqTitle2SidDataset` | 历史标题 → SID | `minionerec/training/rl.py` 使用 |
| `EvalSidDataset` | test 模式仅有输入 token 和 mask | `minionerec/evaluation/evaluate.py` 使用 |
| `SFTData` | 历史标题 → 下一标题 | 主 `minionerec/training/sft.py` 注释关闭；GPR 入口启用 |
| `D3Dataset`、`EvalD3Dataset` | 标题版 RL／评测样本 | 主入口中对应构造被注释 |
| `TitleHistory2SidSFTDataset` | 历史标题 → SID | 主 SFT 关闭；GPR 启用 |
| `RLSid2TitleDataset` | SID → 标题 | 主 RL 构造被注释 |
| `RLSidhis2TitleDataset` | 历史 SID → 下一标题 | 主 RL 构造被注释 |
| `PreferenceSFTDataset` | 历史 → 偏好解释 + SID | 主 SFT 未构造 |
| `UserPreference2sidSFTDataset` | 历史 + 已有偏好解释 → SID | 主 SFT 未构造；GPR 按文件存在性尝试启用 |
| `SidSFTDataset_GPR` | 异构 token prompt 与 `final_value` | 已定义，但 `minionerec/experiments/gpr/sft.py` 当前没有实例化它 |

偏好类从外部 JSON/JSONL 取 `split='train'` 的记录，并从 context 中的 history_items、target_item 构造样本。它们是消费偏好文本的数据集，不是自动从历史在线推理偏好的模型服务。

## 2. `minionerec/training/sft.py`：把现成语言模型变成生成式推荐器

源码：[minionerec/training/sft.py](../minionerec/training/sft.py)，关键类 `TokenExtender`，函数 `train`。

`TokenExtender.get_new_tokens` 遍历索引中每个 token，set 去重后排序。它添加的是每层代码片段，而不是把每个完整商品 SID 当一个新 token。为什么需要排序？使同一份索引的词表扩展顺序稳定，避免依赖 set 的无序迭代。

一个容易忽视的路径细节：`train` 用 `sid_index_path` 的目录和文件名第一个点之前的部分构造 `TokenExtender`，后者又固定追加 `.index.json`。因此传入如 `Dataset.faiss-rq.index.json` 不等于它会按原文件名读取，应核对实际打开路径。

`train` 中最值得顺读的四个区块是：模型加载和词表扩充 → 三个 Dataset → HF Dataset 转换 → Trainer 与保存。文件中的 optimizer/scheduler 辅助定义不是实际训练主循环，阅读时应顺着传给 Trainer 的参数走。

`ConcatDataset` 表示把样本集合拼起来，不是把三种输入同时送进三个编码器。每次模型看到的仍是一条普通 token 序列。共享模型通过不同 prompt 学习不同任务。

## 3. `rq/vae/models/rqvae.py`、`rq.py`、`vq.py`：从连续向量到离散码

源码：[RQVAE](../rq/vae/models/rqvae.py)、[ResidualVectorQuantizer](../rq/vae/models/rq.py)、[VectorQuantizer](../rq/vae/models/vq.py)。

阅读 `RQVAE.forward` 的三行就能把整体结构抓住：encoder 压缩、RQ 量化、decoder 重建。不要先陷入日志和保存代码。`compute_loss` 使用输入向量作为重建目标；`get_indices` 则表明实际导出时只需要前半条路径。

`ResidualVectorQuantizer.forward` 的循环维护两个变量：`residual` 是还没表达的信息，`x_q` 是已经选中向量的累加。每次把该层索引保存在 `all_indices`，最后沿末维 stack。这就是输出 `[B,M]` 的来源。

`VectorQuantizer.forward` 要按下列顺序读：

1. 把输入末维解释成 `e_dim`，flatten 成二维。
2. 必要时 KMeans 初始化码本。
3. 用矩阵运算求所有样本到所有码的距离。
4. 最近邻或 Sinkhorn 后取最大分配，产生整数索引。
5. `nn.Embedding` 查表恢复量化向量。
6. 算 codebook 与 commitment loss。
7. 用 detach 构造直通估计，返回向量、loss、索引。

`.detach()` 决定哪些分支更新谁，是比公式记忆更重要的阅读点。重建不能直接对整数索引反传，所以才需要这个训练设计。

`ResidualVectorQuantizer.__init__` 用 `zip(n_e_list, sk_epsilons)` 建层；两个列表长度不一致时会按较短者截断，并没有先报错。修改层数时不能只改码本数量列表。

## 4. `minionerec/training/rl.py`：定义“推荐得好”的含义

源码：[minionerec/training/rl.py](../minionerec/training/rl.py)，函数 `train` 及其内部 reward 函数。

入口先建立数据和目标映射，再定义 reward 闭包，然后按 `reward_type` 选择函数。这些奖励不需要训练独立神经 reward model：默认正确性和排名奖励直接按字符串比较与候选位置计算。

`reward_type='ranking'` 传入两个 reward 函数，Trainer 对其默认等权相加。`ranking_only` 则只传排名项。把它们写成同一个开关会漏掉监督信号的区别。

另外，入口先加载一次 `llm_model` 用于设备等信息，实际又把 `model_path` 字符串传给 ReReTrainer，后者再次加载模型。这不是把第一次实例化的对象直接交给 Trainer；阅读显存使用时要留意这个事实。

代码中的 `sample_train` 只有开启且模型路径包含小写 `sft` 时，才在 shuffle 后保留索引从 20% 开始的后 80% 数据。它不是一般意义的随机抽取 20%。

## 5. `minionerec/training/trainer.py`：生成和优化之间的桥梁

源码：[minionerec/training/trainer.py](../minionerec/training/trainer.py)，类 `ReReTrainer`。

建议按下面顺序读，而不是从文件中的长 docstring 开始背：

| 方法 | 要观察的对象 | 为什么重要 |
| --- | --- | --- |
| `__init__` | policy、reference、reward、generation config、hash_dict | 决定训练对象和生成规则 |
| `_get_train_sampler` | `RepeatRandomSampler` | 保证同一 prompt 有多条候选 |
| `_prepare_inputs` | prompt → generation → mask → reward → advantage | RL “标签”是在此动态产生的 |
| `_get_per_token_logps` | `[B,C,V] → [B,C]` | 只提取实际生成 token 的概率 |
| `compute_loss` | logps、KL、advantage、mask | 决定真实梯度目标 |
| `prediction_step` | 重新 prepare，再无梯度算 loss | 验证同样包含生成过程 |
| `log` | `_metrics` 的均值与 eval 前缀 | 日志不等于另一个训练目标 |

`_prepare_inputs` 返回的不是普通 SFT batch，而是一组中间量：prompt IDs/mask、completion IDs/mask、reference logps、advantages、sliced_rewards。`compute_loss` 重用这些结果，但对当前 policy 再做一次带梯度的 forward。

为什么要再 forward？生成过程用于离散地决定“这次选了哪些 token”，真正优化需要计算这些被选 token 在当前模型下的可导概率。reward 值不需要对字符串比较求梯度，梯度通过 log probability 传回模型。

可选 `dynamic_sampling` 在非 beam 分支先生成约 1.5G 个结果，再优先保留目标并增加不同结果；`add_gt` 则把部分候选替换成真值。它们改变用于优化的候选分布，不能描述成纯原样采样。`add_gt` 的替换周期还由不同目标数推导，不应想当然等同于每个 prompt 恰好补一条。默认 `scripts/rl.sh` 均关闭。

## 6. `minionerec/evaluation/evaluate.py` 与 `minionerec/evaluation/logits_processor.py`：模型概率变成目录内候选

源码：[minionerec/evaluation/evaluate.py](../minionerec/evaluation/evaluate.py)、[minionerec/evaluation/logits_processor.py](../minionerec/evaluation/logits_processor.py)。

`minionerec/evaluation/evaluate.py` 负责目录、batch 和调用模型；LogitsProcessor 只负责当前步有哪些 token 能选。后者不知道商品标题的业务含义，也不决定 beam 搜索整体策略。

读处理器时追踪 `self.count`：首次拿回答模板后缀作 key，之后拿生成内容作 key。这解释了为何新一批生成必须新建处理器，也解释了 hardcoded prefix 长度和 tokenizer 不匹配时为何会找不到允许 token。

评测的 beam 序列切分 `sequences[:,maxLen:]` 删的是整个 batch 的 padding 后 prompt 宽度，不是每条样本自己的原始长度。因为左 padding 后每条输入都同宽，生成部分起点一致。

## 7. GPR 分支：有哪些实现，哪些没有接通

### 模拟特征，而非真实商业日志

[minionerec/experiments/gpr/amazon18.py](../minionerec/experiments/gpr/amazon18.py) 在历史窗口上随机选 `[CTX_BROWSE]`、`[CTX_SEARCH]`、`[CTX_HOMEPAGE]`；由价格大于 50 或存在已知品牌推导 I/O 类型；价值为 `log1p(price)+log1p(review_count)` 后做 min-max 归一化。用户 token 来自其平均评分阈值。

这些是代码规则生成的模拟字段，不是真实广告曝光、竞价收入或用户上下文埋点。`minionerec/experiments/gpr/convert_dataset.py` 把上下文和用户字段写进 CSV；`SidSFTDataset_GPR` 定义了读取并组合这些信息的路径。

用户特征 JSON 使用原始 reviewerID 作 key，而转换出的 `user_id_original_str` 继承 `.inter` 的重编号字符串；名称中的 original 不保证真的是原始 reviewerID。连通该分支前需要核对映射。

### VAFT loss 的定义与入口脱节

[minionerec/experiments/gpr/sft.py](../minionerec/experiments/gpr/sft.py) 的 `VAFT_Trainer.compute_loss` 在有 `final_value` 时显式做 token CE 和移位，按有效答案 token 求每条序列平均，再计算：

```text
L_VAFT = mean_i( log(1 + final_value_i) × sequence_CE_i )
```

但当前 `train` 导入并构造的是普通 `SidSFTDataset`，不是 `SidSFTDataset_GPR`；第一条训练数据的 keys 没有 `final_value`，后续从这些 keys 构造 HF Dataset 也不会新增它。`compute_loss` 取不到权重就回退到父类 loss。因此不能宣称按当前默认调用已完成价值加权训练。

它确实扩充了异构 special token，并启用了更多标题任务；注册 token 不等于样本已经使用这些 token。偏好文件路径又使用转换后的英文类别描述，需要与实际文件核对。

### HEPO 的 SID 格式问题

[minionerec/experiments/gpr/rl.py](../minionerec/experiments/gpr/rl.py) 的 `parse_sid` 用 `r'\[.*?\]'` 匹配方括号。附带 SID 是 `<a_...><b_...><c_...>`，解析结果为空，分层匹配奖励无法产生设计中的 0.2／0.5／1.0。

原先 `hepo_reward` 只与 SASRec 奖励一起接入；当前已移除 SASRec 分支，因此 `hepo_reward` 保留为实验函数，但不再被入口选择，也没有独立的 `hepo` 选项。主 `scripts/rl.sh` 调的是 `minionerec/training/rl.py`，不是此分支。以上都是入口与格式层面的代码事实，不是对论文方法效果的评价。

## 8. TS-Rec：token 语义初始化和对齐

源码：[minionerec/experiments/ts/sft.py](../minionerec/experiments/ts/sft.py)、[minionerec/experiments/ts/datasets.py](../minionerec/experiments/ts/datasets.py)。

`initialize_sid_token_with_text(model, tokenizer, new_token_id, keywords)`：

```text
关键词字符串 → token IDs [1,T]
→ LLM 输入 Embedding [1,T,H]
→ 沿 T 平均 → [H]
→ 缩放到当前整张 Embedding 的平均行范数
→ 写入 SID token 的输入 Embedding 行
```

这里用的是输入 Embedding 查表，没有把关键词送进完整 Transformer 再取上下文表示；它也只直接写输入权重，未共享输出 head 的模型不会由此自动初始化输出行。

`SidTokenFeatDataset` 将 token 描述文件变成双向任务：单 token → 描述，描述 → 单 token。`minionerec/experiments/ts/sft.py::train` 把它作为第四个 Dataset 加到原有三类旁。TS 入口设置右 padding，和主 `minionerec/training/sft.py` 的左 padding不同。

目录整理时已修正 `scripts/ts_rec_sft.sh`：调用 `minionerec.experiments.ts.sft`，并使用 `ts_rec_data/Industrial_and_Scientific.description_keywords.json`。这是启动脚本修正，TS 的模型和数据处理逻辑未改动；训练仍需配置环境、模型和数据路径。

## 9. 测试证明了什么

[tests/test_datasets.py](../tests/test_datasets.py) 用 MockTokenizer 测 Dataset 初始化、长度和 inputs 属性；没有检查真实 tokenizer 的 SID 原子化，也没有跑 LLM loss、beam 合法性或梯度。文件中还重复定义了同名 `test_SFTData_initialization`，后一个定义覆盖前一个。

[tests/test_minimax_provider.py](../tests/test_minimax_provider.py) 主要测文本 API 辅助工具，部分真实 API 测试需要环境中的 key；末尾还静态检查 Trainer 的测试 generation config 是否设置 top_k/top_p=None。这不能证明所有约束生成路径都正确。

本文没有执行训练、外部 API 测试或 GPU 评测，只做源码与本地数据核对。复现时应以具体 checkpoint、输入文件和实际运行结果为准。
