# 05 从用户历史到推荐结果

[返回目录](README.md) · [上一篇](04_训练流程.md) · [下一篇：核心代码讲解](06_核心代码讲解.md)

## 1. 推理入口吃什么、产出什么

源码：[minionerec/evaluation/evaluate.py](../minionerec/evaluation/evaluate.py) 的 `main`。三个关键资源：

| 参数 | 必须包含什么 |
| --- | --- |
| `base_model` | 训练好的 CausalLM 及匹配的扩充 tokenizer，例如 SFT 或 RL 的 `final_checkpoint` |
| `test_data_path` | 带历史 SID 与目标 SID 的测试 CSV |
| `info_file` | 同一商品体系的 `SID<TAB>标题<TAB>商品ID` 目录 |

输出 `result_json_data` 是样本列表，每条保留 prompt 所用的 `input` 文本和真实 `output`，追加 `predict` 候选 SID 列表。模型输入里没有真实目标，目标只为离线评测保留。

单条用户历史的概念流程是：

```text
已有历史商品编号
→ 用 .index.json 查 SID（CSV 转换阶段已经完成）
→ EvalSidDataset 构造历史 prompt
→ tokenizer → input_ids
→ LLM 自回归预测 SID token
→ 每步约束到合法目录前缀
→ beam 候选 SID 列表
→ 保存 JSON → minionerec/evaluation/metrics.py 与真实 SID 比较
```

`minionerec/evaluation/evaluate.py` 不会在线查询用户数据库，也不接收一串 ASIN 再现场做文本编码和量化。它消费的是已准备好的 CSV。

## 2. 初始化的真实调用顺序

1. 设种子，加载 `AutoModelForCausalLM` 并 `model.eval()`。
2. 读取 info 第一列 SID 和第二列标题，分别构造 `### Response:\n...\n` 文本。
3. 用 checkpoint 的 tokenizer 编码这些目录项，建立前缀允许后继 token 的字典。
4. 选择 SID 约束函数。标题字典也被建立，但标题约束的切换行当前是注释。
5. 设置 EOS 作为 padding，左 padding。
6. 创建 `EvalSidDataset(test=True)`，获得所有 prompt 编码；`get_all()` 单独取得真实目标。
7. 把编码按 `batch_size` 切块，每块调用嵌套 `evaluate`。
8. 将候选回填到结果样本并保存 JSON。

依据：[minionerec/datasets/recommendation.py](../minionerec/datasets/recommendation.py) 的 `EvalSidDataset.pre`。`test=True` 时在追加 `golden_tokens` 之前就返回，因此不会把真实答案拼到模型输入里。这里传入的 `max_len=2560` 也因提前返回而没有实际执行截断，超长输入的可用性仍受模型上下文限制。

## 3. 为什么需要约束生成

LLM 的下一 token 概率分布覆盖全部词表。即使它能生成 `<a_104>`，接下来的 `<b_5><c_9>` 组合也未必属于任何真实商品。独立的 token 都合法，不代表完整 SID 合法。

代码从商品目录建立一种前缀查表结构。例如教学用的目录只有：

```text
<a_1><b_2><c_3>
<a_1><b_2><c_4>
<a_1><b_7><c_8>
<a_9><b_0><c_6>
```

那么开头只允许 a₁ 或 a₉；选择 a₁ 后只能选 b₂ 或 b₇；选到 a₁b₂ 后只能选 c₃ 或 c₄。换行和 EOS 也包含在允许的结束路径中。

这不是向量近邻检索，也不是完整 SID 列表的每项一次性分类。模型每次仍预测一个词表 token，只是非法后继被屏蔽。

## 4. 前缀表到底怎样建立

`minionerec/evaluation/evaluate.py::main` 对每个目录字符串编码，追加 EOS，然后逐个前缀记入 `hash_dict`：

```text
key：前缀 token ID 用 '-' 拼成的字符串
value：当前前缀允许的下一个 token ID 集合
```

`get_hash` 只是字符串连接，不是密码学哈希。首次前缀用回答模板部分；后续前缀只用生成部分。GPT2 路径名取 `prefix_index=4`，其他默认 3；路径名包含 llama 时还去掉编码结果的首 token。

这些是依赖模型名称和 tokenizer 的手写约定，不是动态识别任何模型回答标记的通用算法。因此 checkpoint、目录编码和 prompt 结尾必须与这些假设匹配；换 tokenizer 不保证约束仍正确。

## 5. 每一步 logits 如何被限制

源码：[minionerec/evaluation/logits_processor.py](../minionerec/evaluation/logits_processor.py)，`ConstrainedLogitsProcessor.__call__`。

设一批 B 条历史、beam 宽度 K、当前总长度 Lₜ：

| 变量／操作 | shape |
| --- | --- |
| 传入 `input_ids` | `[B×K,Lₜ]` |
| 当前步 `scores` | `[B×K,V]` |
| `log_softmax(scores)` | `[B×K,V]` |
| 初始全为负无穷的 mask | `[B×K,V]` |
| 允许 token 的 mask 设为 0 | `[B×K,V]` |
| 返回 scores + mask | `[B×K,V]` |

第一次调用取每条序列末尾 `prefix_index` 个 token；后续按 `count` 取已生成的 token。`count` 每次调用增加 1，所以该处理器有状态，不能无条件跨独立生成复用。离线嵌套 `evaluate` 每个 batch 都新建一个处理器，符合这一使用方式。

非法 token 的分数为负无穷，生成器无法正常选它。若找不到任何合法后继，代码发 warning，允许 EOS 尽快结束。这个回退可能留下不完整／无效 SID，因此不能说“无论模型和 tokenizer 如何配置都保证返回有效商品”。

## 6. 一个 batch 的生成过程与 shape

`minionerec/evaluation/evaluate.py` 没有创建 PyTorch DataLoader；它先取出所有样本编码，再用列表切片手工分批。

1. 求该批 prompt 最大长度 P。
2. 左侧补 EOS-as-pad，得到 `input_ids:[B,P]` 和 `attention_mask:[B,P]`。
3. 构造 `GenerationConfig`：`num_beams=K`、`num_return_sequences=K`、`length_penalty`、`max_new_tokens`。
4. 在 `torch.no_grad()` 下 `model.generate(...)`；额外以调用参数显式传 `do_sample=False`，`top_k/top_p` 在配置中设为 None。
5. 返回的 `sequences` 为 `[B×K,P+C]`，C 是本批实际生成后补齐的宽度，不必等于 `max_new_tokens`。
6. `sequences[:, P:]` 去掉 prompt，decode，strip 后按每 K 条分成一个候选列表。

离线 `scripts/evaluate.sh` 示例取 K=50、`length_penalty=0.0`，给每条历史返回 50 个序列候选。`max_new_tokens=256` 是生成上限，不表示每个 SID 需要 256 个 token。

beam search 的含义是同时保留若干较有希望的前缀，再扩展并筛选。`length_penalty=0` 时不额外按长度惩罚调整序列分数。它是在 token 序列空间中做有限宽度搜索，不应承诺等同于穷举所有商品后的严格全局 Top-K。

代码请求 `output_scores=True`，但最后没有把概率分数写入预测 JSON，也没有在 decode 后额外按商品去重或业务规则重排。

## 7. SID 怎样对应到实际商品

目录已经有三列信息：

```text
<a_104><b_118><c_176>    商品标题    118
```

如果只想知道这个 SID 指什么，可以在 info 中查第一列，或把 `.index.json` 反向组织成 `完整 SID → 商品 ID 列表`，再用 `.item.json` 查商品信息。这是解释映射方式，不是说 `minionerec/evaluation/evaluate.py` 已实现了该业务输出步骤。

当前 `minionerec/evaluation/evaluate.py` 的最终预测只保存 SID；`minionerec/evaluation/metrics.py` 也只比较 SID 字符串，不按 info 第三列做商品 ID 判定。`minionerec/evaluation/metrics.py` 中 `item_dict` 保存的是 info 行号列表，主要用于成员合法性检查，并没有据此对碰撞候选做消歧。

两套附带数据确实有 SID 碰撞。所以一个生成 SID 可能对应多个商品，字典反转时必须保留列表才不会静默覆盖。仓库主线没有提供碰撞后的业务选择规则，不能凭文档替它补出“唯一推荐商品”。

此外，主评测没有过滤用户历史上见过的商品，没有库存过滤，没有冷启动新商品自动入库过程。这些均不属于当前实现的输出逻辑。

## 8. 最后如何计算 HR@K 与 NDCG@K

调用链：[scripts/evaluate.sh](../scripts/evaluate.sh) → [minionerec/evaluation/split.py](../minionerec/evaluation/split.py) → 多个 `minionerec/evaluation/evaluate.py` 进程 → [minionerec/evaluation/merge.py](../minionerec/evaluation/merge.py) → [minionerec/evaluation/metrics.py](../minionerec/evaluation/metrics.py) 的 `gao`。

对一条测试样本，找真实 SID 第一次出现在候选列表的位置 j（从 0 开始）：

```text
HR@K(sample)   = 1                         若 j < K，否则 0
NDCG@K(sample) = 1 / log2(j+2)              若 j < K，否则 0
```

最后按测试样本条数平均。每条样本只设一个真实下一商品，所以目标排第一的 NDCG 为 1。代码用自然对数再除以 `1/log(2)`，与上述 log2 形式等价。

教学例子：真实目标是 C，候选为 `[A,C,B]`，则 HR@1=0，HR@3=1，NDCG@3=`1/log2(3)`。奖励函数中的排名惩罚与这里的评测公式不是同一段计算。

`minionerec/evaluation/metrics.py` 的候选 K 集合是 `[1,3,5,10,20,50]`，只打印不超过生成候选数量的 K。它打印无效 SID 计数 `CC`，但遇到命中会 break，所以并非严格扫描完每条列表全部位置后的完整无效率。`CC=0` 本身不能证明所有候选都合法，更不能证明 SID 无碰撞。

## 9. 如何理解“完整推荐结果”的实现边界

本仓库完成的是离线链：已有历史 → prompt → 候选 SID → 与目标比较。数据里存在商品信息，所以人可以追溯到商品；但在线服务、碰撞消歧、过滤和最终展示不是 `minionerec/evaluation/evaluate.py` 的一部分。

还有两个运行层面的源码细节：`scripts/evaluate.sh` 在外部按 GPU 设置环境变量，而 `minionerec/evaluation/evaluate.py::main` 内部再次将 `CUDA_VISIBLE_DEVICES` 设为 `0`；CUDA 初始化时机影响实际设备可见性，不能仅凭 Shell 就保证八个进程正确分散。`minionerec/evaluation/metrics.py` 支持列表形式的 path 参数，但 `n_beam` 和累计数组未在每个文件开头重置；其默认 Shell 单文件调用与手动多文件调用不能混为一谈。

这些问题在本文中只记录，不改动原实现，也不声称已做 GPU 端到端验证。
